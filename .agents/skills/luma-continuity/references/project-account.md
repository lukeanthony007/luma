# Keep the user's outcome distinct from the agent's plan

Use when an ongoing account will guide consequential later work. Preserve the established page layout; these are distinctions to retain, not required headings or a second task ledger.

## User-owned direction

Retain the requested outcome, unresolved requirements and adopted constraints with the user's supporting statement. For a consequential scope choice, keep the relevant wording and its message/source reference or available conversation context. A proposed way to achieve an outcome is not a replacement for that outcome. If no statement adopts a narrower scope, keep the original requirement open.

A source quotation has a limited job: it supports what the user requested or decided. Explain implications separately. Do not attribute an inference, safety preference or implementation recommendation to the user simply because it appears sensible. Preserve negative choices and conditions alongside the decision, without turning them into a universal ban.

## Agent-owned approach

Keep recommendations, assumptions and proposed exclusions distinguishable from adopted choices. Saving, repeating or building on a proposal does not make it agreed. A routine implementation choice can be made within the user's authority without another approval; it still cannot silently remove a requested requirement or be represented as the user's own decision.

When a later message focuses one part of the work, inspect whether it changes the overall outcome or only the current step. Retain other unresolved requirements unless the user changes or cancels them. If scope remains materially ambiguous, state the bounded interpretation or ask the focused question needed for the next action, rather than inventing agreement.

## Current understanding and continuation

Keep supported findings, actual results and consequential unknowns distinct from both direction and approach. Link to underlying evidence and preserve meaningful superseded conclusions as historical. A source change can affect facts, dependent plans and acceptance conditions without changing the user's purpose or authorizing implementation.

On return, check the account's proposed next action against its supporting user statements and relevant present artifacts. Check both directions: does the action preserve all requested requirements, and is each claimed constraint actually adopted or explicitly identified as a proposal? If the account has promoted a recommendation into authority, repair that status and its dependent next actions before continuing within scope.

Before closing work, reconcile new evidence and corrections into the affected account, including implications and remaining requirements. A terse requested answer limits the response, not already-authorized knowledge upkeep. Explicit no-write instructions still take precedence; disclose a consequential stale account without changing it. A preserved account is useful only when later work applies the supported direction correctly.
