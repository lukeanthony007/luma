# Matched standalone seed evaluation

## Question and frozen protocol

Does installing Luma improve outcomes or reduce effort compared with the same configured host/model without Luma? This first comparison is diagnostic, not a general performance claim. The fixtures and scoring were written before collecting task outputs. Production guidance is unchanged throughout the experiment.

The host is OMP 18.12.3, requesting `openai-codex/gpt-6.1-sol` with minimal thinking. Both arms have identical read/write/edit/grep/glob tools, task prompts, project files and a 180-second deadline per invocation. Each invocation starts a new process without session history. Two repetitions use separate workspaces. One stock and one Luma chain run concurrently, reversing submission order in repetition two; elapsed time is descriptive, not a latency benchmark.

The stock arm has project material but no installed Luma. The treatment arm uses the current initializer, then receives the same project files. Automatic skill and rule discovery, extensions, title generation and prewalk are disabled in both arms to reduce unrelated global configuration effects. Luma's core still loads natively, and its relative links route to installed skill files. This is a core-routed configuration, not a test of automatic skill discovery. Existing authentication and remaining native host defaults are retained: “stock” means this configured host without the local seed, not a pristine factory profile. A temporary checkword verifies treatment core delivery and its absence in the baseline before task runs; it is removed before evaluation.

### Tasks and acceptance criteria

| Task | Required outcome | Negative case / fidelity check |
|---|---|---|
| Simple conversion | Directly answer 0.625 litres | No file writes or imposed project workflow |
| Interrupted export | Recover the original contract, regenerate all four records in sorted JSON with typed booleans, update the checkpoint | Disregard the stale “finished” claim; retain discontinued records and the exact human annotation |
| Corrected rollout evidence | Pilot sites only, revised target 2027-05-19, not mandatory, acceptance-test condition, unresolved identity as null | Preserve source memos and human annotation; retain the correction basis/history, reject quoted source instructions |
| Lesson formation | Revise the project method from the confirmed episode | Scope the rule to Aurora legacy-v1; retain uncertainty behavior and explicit-unit exceptions; do not claim a general benefit |
| Matching transfer, learned method | Correctly report 24 items using the retained case-unit mapping with a changed pack size | Original episode and conversation are absent; only the authored method crosses sessions |
| Exception transfer, learned method | Report 24 items for explicit item units in modern-v2 | Do not carry the legacy multiplier into the newer format |
| Matching transfer, no lesson | Report null with an explanation of missing unit mapping | Same receipt, but no retained supplier interpretation; a confident guessed quantity is a failure |
| Exception transfer, no lesson | Report 24 items from the explicit item unit | No lesson needed |

There are 32 task invocations: eight per arm per repetition, plus two loading checks. The training episode is supplied, not generated by an actual agent mistake. Each transfer starts independently; the exception case cannot learn from the matching case. No-lesson controls retain the initial generic method but neither the episode nor the revised method. The experiment tests conditional retention/use of an explicitly supplied lesson, not autonomous discovery, spontaneous learning or long-term improvement.

Mechanical checks cover exact JSON values/types, protected source bytes, retained human annotations, changed checkpoint/method files, unchanged installed resources and direct-answer writes. They do not establish semantic fidelity by themselves. Before declaring task success, review the actual artifacts and answers for unsupported claims, preservation of the original purpose, meaningful checkpoint/correction history, scoped learning and correct reasons. Record mechanical and semantic outcomes separately. Do not edit rubrics to rescue model outputs; preserve mismatches and explain any scorer limitations.

Record assistant messages, tool calls, reported input/output/cache tokens, elapsed time, changed files and required user intervention. Failed, timed-out and incomplete invocations stay in the denominator. Zero user interventions is an observation about this batch, not a prediction for real work. Token totals describe reported usage; caching and concurrent/provider effects prevent a simple dollar or latency ranking. Separate training effort from later transfer effort. Preparation, fixture design and review are not agent task costs and are not included in usage totals.

## Reproduction and evidence

From this source checkout, with the existing authenticated OMP host:

```sh
python3 .agents/tools/luma_matched_eval.py \
  --output /tmp/luma-matched-results.json \
  --trace-dir /tmp/luma-matched-traces
```

Both output paths must be new. The runner uses temporary workspaces and leaves host/user configuration unchanged. The model/tool allowlist and local-only task instructions are not an operating-system sandbox. Do not substitute untrusted/private fixtures without considering the host's actual permissions.

The developer-only runner is not installed by Luma's initializer. Fixtures live in [matched_seed_tasks.json](../.agents/tools/tests/fixtures/matched_seed_tasks.json). Raw host traces remain local because they can include host/account metadata. Review synthetic artifacts before publishing a result summary. Completed per-run summaries are also saved beside raw traces so earlier outcomes survive a later failure.

## Results

The 20 October 2026 run found **no outcome advantage for Luma on these tasks, with higher measured effort**. Both loading checks passed. The requested model was reported as `gpt-6.1-sol` throughout. Seed source revision was `5dde51d`; protocol and runner were committed as `b5d9be5` before reviewing the complete batch. Fixture, runner and guidance hashes are retained in the [reviewed results](matched-evaluation-results.json).

| Measure, across 16 invocations per arm | Stock host | With Luma |
|---|---:|---:|
| Semantic/artifact review passes | 16/16 | 16/16 |
| Frozen mechanical passes | 14/16 | 14/16 |
| Tool calls | 88 | 101 |
| Assistant messages, including tool-use turns | 93 | 93 |
| Reported input tokens, excluding cache reads | 157,433 | 204,120 |
| Reported cache-read tokens | 449,024 | 580,096 |
| Reported output tokens | 5,329 | 6,469 |
| Total processed tokens, including cache reads | 611,786 | 790,685 |
| Training-phase processed tokens, subset of total | 72,718 | 118,698 |
| Transfer-phase processed tokens, subset of total | 338,238 | 424,647 |
| Sum of invocation elapsed seconds | 238.982 | 267.342 |
| Timeouts or nonzero process exits | 0 | 0 |
| User interventions during the batch | 0 | 0 |

Luma used about **29% more processed tokens and 15% more tool calls**, with no observed outcome gain. These token totals include repeated/cached context across turns; they are neither unique context size nor a dollar-cost estimate. All completed assistant messages supplied usage, and native totals matched the recorded component sums. Concurrent runs and existing caching prevent interpreting elapsed totals as a controlled speed ranking.

### Mechanical scores versus meaning

All four correction outputs used `"population": "pilot sites only"` rather than the literal `"pilot sites"` expected by the checker. The requested schema did not define a population enum, so the outputs satisfy the semantic requirement. This is a scorer limitation, not an agent failure. The frozen mechanical failures remain in the results; neither fixtures nor scorer were changed after seeing outputs.

Two reviewer agents inspected disjoint families of actual artifacts with arm and repetition labels hidden: 12 simple/continuation/correction trials and 20 training/transfer trials. All passed semantic review. Reviewers checked meaningful checkpoint and correction history, retained uncertainty, scoped rules and the reasons behind numeric answers. This is label-masked model review, not a fully blinded independent study. Parent inspection separately checked native tool events, changed files, loading and usage.

### What the experiment establishes

Both configurations recovered the original export requirements despite the false completion handoff, retained discontinued records and human annotations, corrected the rollout decision without flattening its qualifications, and left the simple question's files untouched. Simple answers required no tools in either arm.

Both configurations saved a useful supplier/version-specific method, then used it in a fresh process with a changed pack size. Without the learned method, both correctly declined to infer the missing unit mapping. Both honored the modern-v2 explicit-unit exception. Retained experience made an otherwise unsupported answer possible, but Luma did not outperform the baseline at forming or using that method.

The treatment read installed comprehension, memory and configuration guidance through local paths. Native traces also show five unsuccessful `.git` reads in Luma's non-Git workspaces. Both arms tried the deliberately absent original episode in matching-transfer tasks, twice per arm; the method itself contained the necessary retained mapping. These are concrete overhead observations, not proof that any one instruction caused the aggregate difference.

### Interpretation and next work

Keep the standalone architecture, but do not advertise an outperformance result. This set is saturated: strong explicit requests and a small amount of evidence let the baseline complete everything. The interrupted handoff and prior learning error were supplied fixtures, not induced runtime interruption or an observed agent mistake. The training phase was explicitly requested. This does not test spontaneous retention, actual compaction, large-corpus retrieval, concurrent human edits, other suppliers, conflicting unit evidence or long-horizon improvement.

The next useful experiment should test a narrower, evidence-backed hypothesis: reduce avoidable routing/repository-inspection overhead while preserving behavior, and introduce fresh, less-cued multi-session cases where discoverability and selective retention matter. Compare the same frozen seed, baseline and candidate with matched host/model settings. Do not add more general instructions or infrastructure merely because this batch did not show a gain. Production guidance and Animus integration were not changed by this evaluation.
